# 線の参照（annotation_ref）の検証

線（annotation）には id が無い。`EditAnnotationDialog` と行内のラベル editor は、開いた線を
`TAnnotationRef` で指し、描画のたびに `resolve_annotation_ref` で配列の位置に解き直す。
別のクライアントの保存が届くと配列は丸ごと置き換わり、位置はずれる。
この解決が「開いた線」を指し続けるかを、Lean 4 で一般に証明し、小さな配列で全数検査する。
Mathlib は使っていない。

```sh
export PATH=$HOME/.elan/bin:$PATH   # elan は verification/lean-nest/README.md の手順で入れる
lake build && .lake/build/bin/check  # 合わせて 30 秒ほど（検査は約 7 秒）
```

0 以外で終わるのは次のとき。

- `lake build`：証明が崩れた。`sorry` が残っている（`lakefile.toml` の `warningAsError` で、警告は error）。
- `check`：安全なはずの場合で、解決が別の線を指した。崩れるはずの場合（今のコードの重複、
  修正案でも避けられない場合、わざと壊した版）で、期待した反例が出なくなった。
  同じ items の線が無い場合に、修正案と今のコードの答えが違った。

`lake env lean Axioms.lean` で、定理が `sorryAx` に頼っていないことを見られる。

## 写したもの（4ff6400 と、この PR）

| コード | モデル（`AnnotRef/Model.lean`） |
|---|---|
| `TLineAnnot` | `Line`：`items` と、属性（heads・label・is_doubled・custom）をまとめた 1 つの数 `attr`。`id` はコードに無い「本当はどの線か」の印で、判定にだけ使う |
| `ref_of_annotation` / `resolve_annotation_ref`（4ff6400） | `refOf` / `resolve`：同じ位置の線の items が同じならその位置、そうでなければ items が同じ最初の線、無ければ null |
| 同（この PR） | `refOfF` / `resolveF`：同じ items の線のうち何番目か（`nth`）と、何本あったか（`count`）。本数が同じなら `nth` 番目、違えば null |
| `add_arrow` | `append`：末尾に足す |
| `EditAnnotationDialog` の Delete | `deleteLine`：`filter((_, i) => i !== index)` |
| ラベル・太さ・不透明度・矢印の大きさ・向きの反転（`heads` だけ） | `setAttr`：`items` を変えない |
| `update_annotation_after_deletion`（アイテムの削除。読み込み時の `repair_nest` も同じ形） | `deleteItem`：items から最初の 1 つを取り除き、2 未満の線を消す |
| `handle_making_line` の "delete" | `deletePair`：2 点を（どちら向きでも）結ぶ線を全部消す |
| （アプリはしない） | `prepend`（先頭に足す）、`swap`（隣と入れ替える） |

開いた後、参照は変わらない（`clicked_annotation` も `editing_line_label.target` も、開く時にだけ作る）。
別のクライアントの保存が届くたびに解き直し、null になったらダイアログ・editor は閉じる
（`EditAnnotationDialog` の `target_gone`、`AnnotationLayer` の `editing_target_gone`）。

写したファイルの blob は `modeled-sources.txt` にある。

捨てたもの:

- 線の描画、当たり判定、ダブルタップの判定（`lineLabelLastTap` は位置で引くが、300ms の間のこと）。
- 描画とイベントの間に保存が届く隙（ハンドラは最後の描画の `annotations` と位置で参照を作るので、
  両者は食い違わない）。
- items に同じアイテムが 2 度ある線。アプリは作らない（`handle_making_line` は始点と終点が同じなら
  線を作らない）。JSON の読み込みや `API.add_arrow` では作れるが、調べていない。

## 性質

開いた線（id `t`）について、保存が届くたびの解決の結果を次のどれかに分ける。

| 結果 | 意味 |
|---|---|
| **別の線** | 解決が、`t` ではない線の位置を返した。ユーザーは気づかずに別の線のラベル・太さを変え、削除する |
| 閉じた（残っていたのに） | `t` が items も変わらず残っているのに null。ダイアログ・editor が閉じるだけ |
| 閉じた（消えた・items が変わった） | `t` が消えたか、items が変わって null。正しい |
| 正しい | 最後まで `t` を指した |

守りたいのは「別の線を指さない」。閉じるのは、やり直せば済む。

## 一般の証明（`AnnotRef/Proofs.lean`）

配列の長さ・items の形を問わない。

| 定理 | 内容 |
|---|---|
| `resolve_safe` | items が参照と同じ線が `t` だけなら、今のコードは別の線を返さない |
| `resolve_live` | `t` が items を変えずに残り、同じ items の線が他に無ければ、今のコードは `t` の位置を返す |
| `resolveF_hasItems` | 修正案が返す位置の線は、参照と同じ items を持つ |
| `refOfF_unique`・`resolveF_eq_resolve` | 開いた線の items が他と重ならず、今の配列でも同じ items の線が 1 本以下なら、修正案は今のコードと同じ答え |
| `resolveF_correct` | 同じ items の線の顔ぶれ（id の並び）が開いた時と同じなら、修正案は `t` の位置を返す |
| `no_resolver_without_id` | id が無い限り、どんな規則でも「何も変わらなければ開いた位置を返す」なら、「線 0 を消し、同じ items の線を末尾に足す」1 回の保存で別の線を返す |

「1 回の操作の後、同じ items の線の本数が同じなら顔ぶれも同じ」（修正案が別の線を指さない理由）は、
一般には証明していない。全数検査の R2・R3 で確かめた。

## 全数検査（`AnnotRef/Check.lean`）

アイテムは {0,1,2}。線の items の候補は 2 点の順序つきの組 6 通りと 3 点の線 2 本の 8 通り。
初めの配列は線 1〜3 本の 584 通り。そのすべての線を開き、相手のクライアントの操作を届ける。
アプリの操作は 1 つの配列につき約 25 通り（末尾に足す 8、線を消す、属性を変える、アイテムを消す 3、
線の削除モード 3）。

| 場合 | 通り | 今のコード | 修正案 | M1 | M2 | M3 |
|---|---:|---:|---:|---:|---:|---:|
| R1. アプリの操作 1 回・同じ items の線が無い | 18,376 | 0 / 0 | 0 / 0 | 2,336 / 0 | 0 / 0 | 0 / 0 |
| R2. アプリの操作 1 回・同じ items の線がある（前か後） | 14,776 | **820** / 0 | 0 / 2,354 | 1,524 / 0 | 344 / 192 | 2,638 / 2,354 |
| R3. 保存 2 回（届くたびに解き直す） | 653,004 | **30,818** / 0 | 0 / 83,182 | 155,376 / 0 | 13,080 / 6,086 | 54,560 / 77,356 |
| R3n. R3 のうち、同じ items の線が無い | 295,310 | 0 / 0 | 0 / 0 | 78,218 / 0 | 0 / 0 | 0 / 0 |
| R4. 1 回の保存に操作 2 つ | 653,004 | **34,402** / 0 | **8,412** / 70,958 | 158,608 / 0 | 18,336 / 5,116 | 46,464 / 70,958 |
| R4n. R4 のうち、同じ items の線が無い | 312,076 | **5,916** / 0 | **5,916** / 0 | 83,684 / 0 | 5,916 / 0 | 5,916 / 0 |
| R5. 先頭に足す・隣と入れ替える（アプリはしない） | 16,576 | **3,400** / 0 | **272** / 1,672 | 15,552 / 0 | 1,944 / 0 | 1,720 / 1,672 |
| R5n. R5 のうち、同じ items の線が無い | 7,896 | 0 / 0 | 0 / 0 | 7,224 / 0 | 0 / 0 | 0 / 0 |

各欄は「別の線 / 閉じた（残っていたのに）」。M1〜M3 はわざと壊した版（下の「検査が効くこと」）。
同じ items の線が無い場合（R1・R3n・R4n・R5n）では、修正案と今のコードの答えは届くたびにすべて同じ（0 件の違い）。

### 分かったこと

1. **同じ items の線が無ければ、今のコードは別の線を指さない**（R1・R3n・R5n、と `resolve_safe`）。
   前に足す・消す・並べ替える・属性を変える、のどれでも同じ線を指し、線が消えれば null になる。
2. **同じ items の線が 2 本あると、今のコードは別の線を指す**（R2・R3）。2 点を結ぶ線と矢印を
   両方引くと、2 本は同じ items になる。最短の例:
   - 同じ items の線 D1・D2 の D2 を開く。相手が手前の関係ない線を消す → D2 の位置に何も無くなり、
     「items が同じ最初の線」の D1 を返す（`[P–Q, D1, D2]` → `[D1, D2]`）。
   - D1 を開く。相手が D1 を消す → 同じ位置に D2 が来て、items が同じなので D2 を返す。ダイアログは閉じない。
   - 線 Z–W、3 点の線 A–B–Z、線 A–B の A–B を開く。相手がこざね Z を消す（`update_annotation_after_deletion`）
     → Z–W は消え、A–B–Z は A–B に縮む。A–B の元の位置に何も無くなり、縮んだ方を返す。
   どれも本物のコードの vitest で再現した（`src/Dialog/EditAnnotationDialog.test.tsx`、
   `src/utils/annotation_ref.test.ts` の「with lines of the same items」）。
3. **修正案は、アプリの操作が 1 回ずつ届く限り別の線を指さない**（R1〜R3）。同じ items の線の本数が
   変わったら閉じる。その代わり、開いた線が残っていても閉じることがある（R2 で 2,354 通り。
   たとえば同じ 2 点に線をもう 1 本引かれた）。
4. **1 回の保存に「開いた線を消す」と「同じ items の線を足す」が入ると、どんな規則でも防げない**
   （R4n・`no_resolver_without_id`）。コードから見える配列が、何も起きなかった場合と同じになるため。
   防ぐには線に id を持たせるしかない。
5. 線の items が変わる操作（アイテムの削除で縮む）の後は、どちらの版も、開いた線を見失う（閉じる）。
   向きの反転は heads だけを変えるので、同じ線を指し続ける。

## 検査が効くこと（変異）

`check` は、次の 3 つのわざと壊した版でも毎回走り、反例が出なければ失敗にする。

| 変異 | 期待する反例 | 結果 |
|---|---|---|
| M1. 今のコードから、同じ位置の items の確かめを抜く（位置が範囲内ならそれを返す） | R1（同じ items の線が無くても） | 2,336 件。例: `[[0,1], [1,0]]` の線 0 を開き、線 0 を消す → 線 [1,0] を返す |
| M2. 修正案から本数の確かめを抜く | R2 | 344 件。例: 同じ items の 2 本の 1 本目を開き、それを消す → 残った方を返す |
| M3. 修正案で何番目かを見ず、最初の線を返す | R2 | 2,638 件 |

モデルそのものを書き換えた場合も確かめた（コードを壊したのと同じ）。

- `resolveF` の `m.length = r.count` を `true` にする → `lake build` は証明（`resolveF_eq_resolve` など）が崩れて失敗し、
  `check` は「R2 / 修正案: 別の線を指した」「R3 / 修正案: 別の線を指した」で 1 を返す。
- `resolve` の items の確かめを `r.index < ls.length` にする → `lake build` は `resolve_hasItems` が崩れて失敗し、
  `check` は R1・R3n・R5n で別の線を指し、「修正案と今のコードの答えが違う」で 1 を返す。
- `Proofs.lean` に `sorry` の定理を足す → `lake build` が失敗する。

## モデルとコードのずれ

`modeled-sources.txt` の blob と、今のファイルの `git hash-object` を比べる。違っていたら、
参照の作り方・解決・線の配列を変える操作が変わったかを見て、モデルを写し直し、行を足す。
