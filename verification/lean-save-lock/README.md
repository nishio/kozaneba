# 保存の楽観ロック（#98）のモデル検査

2 つのクライアント（端末・タブ）が同じ ba を編集・保存し、互いの保存を snapshot で受け取る。この流れを Lean 4 で写し、すべての手順の並びを幅優先で調べる。性質が崩れたら、そこに至る最短の手順を出す。Mathlib は使っていない。

```sh
export PATH=$HOME/.elan/bin:$PATH   # elan は verification/lean-nest/README.md の手順で入れる
lake build && .lake/build/bin/check  # 約 50 秒（並列で 4 分ぶんの CPU）
```

終了コードが 0 でなくなるのは、次のどちらかのとき。

- 安全なはずの構成で、性質が崩れた。
- 崩れるはずの構成（直していない危険、わざと壊した版）で、期待した反例が出なくなった。

## 写したもの（4ff6400）

| コード | モデル |
|---|---|
| `mark_local_changed` | 編集：`is_local_change = true`、`last_updated` に時計の値。内容は「編集の集合」で表す |
| `LocalChangeWatcher` | `is_local_change` なら false にして `save()` |
| `save()` | ログインしていなければ dialog だけ出して戻る。conflict 中は書かない。それ以外は `note_own_write`、`begin_write`、transaction |
| `write_if_not_changed` | commit の時点で、クライアントの今の base / own を見て判定する 1 手（Firestore は、読んだ doc が変わると関数ごとやり直すため） |
| then / catch | `end_write`。done は版が今の `last_updated` と同じときだけ。conflict → `save_conflict`。一時的なエラー → retry。それ以外 → `save_error` |
| `set_up_read_subscription` の snapshot | 同じ版なら base を更新。own なら無視。保存していない変更があれば conflict。それ以外は置き換える。snapshot は順に届き、途中を飛ばしてよい |
| `SaveErrorAlert` を閉じる | `save_error = ""` |
| conflict で「再読み込み」 | サーバの版を開き直す |

写したファイルの版は `modeled-sources.txt` にある。CI は、ファイルの今の blob がこの一覧に無いと warning を出す。

捨てたもの:

- 中身（アイテム）の形。内容は編集の集合だけで表す。
- `writers` や `anyone_writable` の扱い。
- 下書き・backup・`read_doc` の時計の補正。
- 新しい ba を作る保存（`initial_save` / `save_new`）。

## 性質

| | 性質 | 崩れると何が起きるか |
|---|---|---|
| P1 | サーバに書くとき、サーバにあった編集がすべて書く内容に入っている | 誰かの編集をサーバで上書きして失う |
| P2 | snapshot で手元を置き換えるとき、手元の編集がすべてサーバの版に入っている | 手元の編集を、確認なしに失う |
| P3 | done にするとき、手元の編集がサーバに載っているか、まだ保存が続く | 保存済みと表示されるが、載っていない |
| P4 | 手元にサーバに無い編集があるなら、保存か、何かの印が残っている（印は `is_local_change`・書き込み中・retry・`save_error`・conflict・届いていない snapshot） | 保存されないのに、誰も気づけない |

### 見つかったこと

1. **一時的なエラーの後に、同じ版を二重に書く（B, B4）。**
   - v1 の保存が一時的なエラーになった。その間に v2 の保存も出ている。
   - retry は、今の状態（v2）をもう一度送る。v2 が 2 回送られる。
   - 後から実行された 2 回目は、サーバが自分の同じ v2 なのに書き直す。条件が `server_version > version` で、等しいときは書くため。
   - その間に別の端末 c1 が v2 を取り込み、v3 を保存していると、c1 には二重の v2 の snapshot が自分の v3 の後に届き、手元が v2 に戻る（P2）。
   - 続いて届く v3 は「自分の古い保存の ack」として無視されるので、戻ったまま。
   - 次に編集すると、サーバの v3 を自分の版として上書きし、v3 の編集を失う（P1）。
   - **未確認の前提**: 内容が同じ書き直しで、Firestore の SDK が snapshot を出すか。出さないなら、この連鎖は起きない。
   - **修正案 1**: 条件を `>=` にする。二重の書き込みが無くなるだけなので、どちらにしても害は無い。
2. **エラーの表示を閉じると、「保存できていない」印が消える（D）。**
   - `SaveErrorAlert` の `onClose` が `save_error` を空にする。
   - 保存に失敗した変更が、どこにも印が無いまま残る（P4）。
   - 別の端末の保存が届くと、確認なしにそちらに置き換わる（P2）。手元の backup には残る。
   - **修正案 2**: 表示だけを閉じ、`save_error` は次に保存が成功するまで残す。
3. **ログインせずに anyone_writable の場を編集すると、印が消える（E）。**
   - `LocalChangeWatcher` が `is_local_change` を下ろしてから `save()` を呼ぶ。`save()` はログインしていないと dialog を出して戻る。
   - 変更は保存されず、印も残らない（P4）。別の端末の保存で置き換わる（P2）。
   - **修正案 3**: ログインしていなければ、watcher は `is_local_change` を下ろさない。dialog を出すだけにする。
   - なお、`CloudSaveDialog` の「続ける」は `initial_save()`（新しい ba を作る）を呼ぶ。他人の場を編集していた場合の扱いは、別に確かめる必要がある。
4. **版が `Date.now()` なので、時計の値が重なったり戻ったりすると壊れる（F, G）。**
   - 2 つの端末が同じミリ秒に保存すると、相手の版を自分の版と見なして上書きする（P1）。
   - 1 つのタブで、同じミリ秒に 2 回保存した場合や、時計が戻った場合（NTP の補正など）も壊れる。古い内容で書き直す（P1）、または新しい保存を「書かない」で終えて done にする（P3, P4）。
   - **修正の方向**: 版を、タブの中で必ず増え、端末どうしで重ならない値にする。たとえば `max(Date.now(), 前の版 + 1)` に、端末ごとの乱数の端数を足す。A の構成（時計は全体で一意に増える）は、この修正の後の状態を表す。

## #141 で直したもの

修正案 1〜3 と、版をタブの中で必ず増やす変更（`mark_local_changed` の `max(Date.now(), last_updated + 1)`）は #141。構成 H が #141 の後のコードに当たる。残るのは、端末どうしで同じミリ秒になる場合（構成 F）。

## 調べていないこと

- 3 つ以上のクライアント。
- 編集が 5 回以上。
- 1 つのクライアントの transaction のやり直しの細部（モデルでは commit の時点の 1 手）。
- snapshot が、自分の commit の応答より遅れて届く順序の、実際の頻度。
- オフラインのときの Firestore の内部キュー（transaction はオフラインでは送られずに失敗するので、retry として写した）。
